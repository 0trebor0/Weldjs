Overview

WeldJS runs server-side JavaScript inside otherwise untouched HTML files.

An HTML file passes through byte for byte, except for <weld> blocks. The page is compiled once at startup; each request re-runs only the blocks that produce data. There is no HTML parser involved at any point — non-<weld> bytes are never inspected.

The one thing to know first. There are two kinds of block and they behave completely differently:

<weld>              runs ONCE at load, shared by every request
<weld var="x">      runs on EVERY request, private to that request

Put shared setup in the first, anything derived from the request in the second. Mixing them up lets one user's data reach another — see Request isolation.

Requires Node.js 20 or newer. No dependencies.

Quick start

npm test     # run the test suite
npm start    # serve example/page.html on 127.0.0.1:3000
npm run bench

Minimal page:

<weld>
const db = require('./db.js');
</weld>

<h1>Users</h1>

<weld var="users">
return await db.users();
</weld>

<script>
console.log(weld.users);
</script>

Tutorial: a profile page

You will build a page that reads a user from SQLite and renders it, served by Express. Every code block is complete — nothing is elided.

1. The page

Create views/profile.html:

<!doctype html>
<html>
<head><meta charset="utf-8"><title>Profile</title></head>
<body>
  <h1>Profile</h1>
  <pre id="out"></pre>
</body>
</html>

No <weld> blocks yet, so this file passes through unchanged.

2. Serve it

'use strict';

const path = require('node:path');
const express = require('express');
const { load } = require('./src');

// Returns immediately and compiles in the background, so no async wrapper is
// needed. Setup <weld> blocks run once, here, not per request.
const page = load(path.join(__dirname, 'views', 'profile.html'));

const app = express();

// page.handler renders, ends the response, and forwards any failure to
// Express's error middleware. No async wrapper, no res.end(), no try/catch.
app.get('/profile', page.handler);

app.listen(3000, () => console.log('http://127.0.0.1:3000/profile'));

Load once, outside the route. Calling load or compileFile inside the handler would recompile the file and re-run your setup on every request, defeating the entire design. load caches by resolved path, so a stray second call returns the same page rather than compiling twice.

3. Add a setup block

Add this just inside <body>:

<weld>
const { DatabaseSync } = require('node:sqlite');

const db = await shared('app-db', async () => {
  const connection = new DatabaseSync(':memory:');
  connection.exec(`
    CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT);
    INSERT INTO users (name) VALUES ('Rob'), ('Sarah');
  `);
  return connection;
});

const findUser = db.prepare('SELECT id, name FROM users WHERE id = ?');
</weld>
  • require works here and resolves relative to the HTML file, not your CWD.
  • shared(key, factory) caches a resource across pages. The factory runs once; concurrent callers receive the same promise.
  • db.prepare(...) compiles the SQL once. The ? is a placeholder that holds no data — preparing it here does not bind it to a particular id.
  • Top-level await is allowed in setup blocks. That is why compileFile is async.

4. Add per-request data

Add this after the <h1>:

<weld var="profile">
const id = Number(request.query.id);

if (!Number.isInteger(id) || id < 1) {
  return { error: 'bad id' };
}

const row = findUser.get(id);
return row ? { id: row.id, name: row.name } : { error: 'not found' };
</weld>

This runs on every request. request is whatever you passed to page.render — with Express that is req, so request.query, request.params, and request.body all work.

findUser is shared, but .get(id) is called with this request's id and returns a fresh row. id and row are declared inside this block, which is what keeps them private to one request.

5. Use it client-side

The block is replaced at render time by a script tag, so profile is a normal variable for anything after it:

<script>
  document.querySelector('#out').textContent = JSON.stringify(weld.profile, null, 2);
</script>

GET /profile?id=1 and ?id=2 hit the same cached buffers and the same handler, differing in one line:

<script>(window.weld=window.weld||{}).profile={"id":1,"name":"Rob"};</script>
<script>(window.weld=window.weld||{}).profile={"id":2,"name":"Sarah"};</script>

The two block types

This is the whole model. Everything else follows from it.

BlockRunsScopeUse for
<weld> Once, at compile Shared by every request, for the process lifetime modules, connections, prepared statements
<weld var="x"> Every request Locals are private to that invocation anything derived from the request

Setup blocks are concatenated in document order into a single page closure, so a const declared in the first is visible in the second and in every handler.

A var block is compiled into async function (request, response) { …your code… }, so it must return a value, and it may await.

Accessing req and res

A plain <weld> block cannot see them at all. It runs once at compile time, before any request exists. Referencing request there throws ReferenceError: request is not defined — and because setup runs during compileFile, that failure stops your server at boot.

They are available only inside <weld var="…"> blocks, where they are the two handler parameters, named request and response:

<weld var="profile">
const id = request.query.id;      // Express req
response.setHeader(...);          // Express res — see caveats below
return { id };
</weld>

Whatever you pass to page.render(req, res) is what these names refer to, so with Express they are the full Express req/res, including request.query, request.params, and request.body.

Two caveats on response

It is null under renderToBuffer() unless you pass one explicitly, since that signature is renderToBuffer(request, response = null). A handler that touches response unconditionally will throw there.

Headers can be set from a block, because blocks all run in phase one, before anything is written:

<weld var="profile">
response.setHeader('cache-control', 'no-store');   // fine — nothing written yet
return { id: 1 };
</weld>

Use setHeader rather than writeHead in your route. writeHead marks the headers as sent immediately, which prevents render() from adding Content-Length:

// handler sets content-type only if nothing already has.
app.get('/profile', page.handler);

// Setting your own headers first still works — use setHeader, not writeHead.
app.get('/no-cache', (req, res, next) => {
  res.setHeader('cache-control', 'no-store');
  page.handler(req, res, next);
});

If several blocks need the same per-request value, compute it in each — they run concurrently, so there is no ordering between them, and stashing it in setup scope would leak across users (why).

Compile and render

What compilation produces

compileFile reads the file once and returns a frozen page object holding:

  • Static HTML as buffers. Runs of HTML separated only by a setup block are joined once at compile time, so rendering writes one buffer per run.
  • One handler function per var block.

Nothing is re-scanned or re-parsed per request.

What a request does

render() works in two phases.

  1. Resolve. Every var block runs concurrently. Nothing is written yet.
  2. Emit. Each value is serialized, the total byte length is computed and set as Content-Length, and the parts are written in document order.

Blocks run concurrently because they are independent by construction: anything shared between them would have to live in setup scope, which is shared across requests and therefore already unsafe. Total time is the slowest block rather than the sum:

Page with 3 blocks, ~10 ms eachTime
sequential42.9 ms
concurrent (current)14.4 ms

Nothing is sent until the whole response is known to succeed. A block that throws — or returns a value that cannot be exported — fails with zero bytes written, so the caller can still send a real error status. The response goes out complete, with Content-Length rather than chunked encoding.

Static parts are buffers computed at load time, so emitting is a few microseconds. The per-request cost is dominated by whatever your blocks actually do.

Request isolation

The rule. Anything derived from request lives in a var block. Setup scope is only for things identical for every user.

The lifecycle

A setup block runs once, when the page is compiled, and its declarations live in one closure that every subsequent request shares for the life of the process. It is process-shared state, not per-request state. Writing request data into it leaks across users. This is invisible in single-user testing — you need concurrency and an await to see it.

That makes setup scope right for exactly three things:

  • Immutable configuration — values read once and never written.
  • Shared service or client instances — a database handle, an HTTP client, a prepared statement. Created once, used by everyone, deliberately.
  • Caches and resources you intend to share — where every user seeing the same entry is the goal rather than an accident.

Anything else — anything whose correct value depends on which request is being served — belongs in a var block.

const is not a safety boundary. The compile-time warning flags top-level let and var in setup blocks, because a reassignable binding is the cheapest signal of a leak. It is a heuristic and nothing more. A const binding cannot be reassigned, but its contents can still be mutated, and a mutated shared object leaks in exactly the same way:

<weld>
const seenUsers = [];          // const, no warning, still shared by everyone
</weld>
<weld var="page">
seenUsers.push(request.query.user);   // every user's name, visible to every user
return { seen: seenUsers };
</weld>

Silence from the warning means only that no reassignable binding was found. It is not a statement that the page is request-safe.

The safe version of the same shape keeps the per-request value local, and keeps in setup only the thing that really is identical for everyone:

<weld>
const db = await shared('db', () => openDatabase());   // one handle, deliberately shared
</weld>
<weld var="page">
const user = request.query.user;              // local to this invocation
const rows = await db.recentFor(user);
return { user, rows };
</weld>

Wrong. currentUser is shared by every request.

<weld>
let currentUser = null;
</weld>
<weld var="profile">
currentUser = request.query.user;
const row = await lookup(currentUser);   // yields here
return { name: currentUser };            // may now be another user's value
</weld>

Two concurrent requests, one asking for alice and one for bob:

req A (asked for alice): {"name":"bob"}
req B (asked for bob):   {"name":"bob"}

Alice received Bob's data. A writes currentUser, then awaits; B overwrites it during that await; A resumes and reads B's value.

Right. The value is a local, private to this invocation.

<weld var="profile">
const currentUser = request.query.user;
const row = await lookup(currentUser);
return { name: currentUser };
</weld>

Interleaving only happens at await points. A shared object touched synchronously is safe — this is why a shared prepared statement is fine, since node:sqlite's DatabaseSync never yields mid-query. A shared variable held across an await is not. shared() is safe for the same reason: a connection handle is immutable state that is genuinely identical for all users.

Exporting data

A var block's return value is serialized into a <script> tag. It must be JSON-compatible: strings, finite numbers, booleans, null, arrays, and plain objects. Object.create(null) is accepted.

The browser contract

Exports land on a single window.weld object, one property per var block:

<weld var="users">return await db.users();</weld>

emitted: <script>(window.weld=window.weld||{}).users=[…];</script>
browser: weld.users

One global rather than one per export. A bare const users would be a name no other script on the page could use, and a second declaration of it — from a CDN script the compiler cannot see — is a SyntaxError that disables every script on the page while the server still returns 200.

  • The guard is idempotent. Each block emits its own <script> and any of them may run first, so every one creates the namespace if it is missing and reuses it otherwise. Block order does not matter.
  • Exports overwrite. If the property already exists, the export replaces it. Other properties on the object are left alone.
  • Nothing else is defined. No bare global is created; weld is the only name the page takes.

Everything else is rejected with a TypeError naming the path:

RejectedWhy
undefined, functions, symbols, bigintsno JSON representation
NaN, Infinityno JSON representation
circular referencescannot be serialized
Date, Map, Set, class instancesnon-plain objects; return date.toISOString() instead
a __proto__ keywould set the prototype of the client object
nesting deeper than 64 levelsbounded to prevent stack exhaustion
more than 1 MiB per renderbounded so an unbounded query cannot be serialized into the page

What the size limit measures

The limit is 1 MiB (1,048,576 bytes) of emitted <script> payload, measured in UTF-8 bytes, summed across every block on the page, per render. Three parts of that are worth stating separately:

  • The whole element counts, not just the JSON: the <script> tags, the window.weld assignment and the nonce attribute are all charged. The same data can fit without a nonce and not fit with one.
  • Bytes, after escaping. <, > and & each become a six-byte \uXXXX escape, and a character outside ASCII costs two to four bytes. A 200,000-character string of < is 1.2 MB of payload and is rejected.
  • Per render, shared by the page. One budget covers every var block, so five blocks cannot each spend the full megabyte. Each render starts fresh.

The check happens in two stages. A cheap lower bound is spent as the value is walked, so a result that cannot possibly fit fails before the whole structure has been copied, with the path where it ran out:

Cannot export more than 1048576 bytes per page; limit reached at $[8421].email

Whatever survives that is serialized and then measured for real, which is the check that actually defines the limit:

<weld var="rows"> in /app/page.html: Cannot export more than 1048576 bytes per page;
the emitted <script> payload reached 1200028 bytes

Raise it per page with compileSource(src, { maxExportBytes }), which validates the value at compile time rather than on the first request. But if you are approaching the default, the data almost certainly wants paginating or fetching from the client rather than inlining into the document.

See Security for why these are enforced rather than conveniences.

Variable names

The var attribute becomes a property on the export namespace, weld.<name>. It must be a valid identifier and unique across the page, both enforced at compile time.

Reserved words are rejected as well. As a property name a reserved word is in fact legal — weld.class parses — but the restriction predates the namespace and is kept, since relaxing it would widen what pages may declare and narrowing it again later would be breaking.

Do not declare weld yourself. A top-level var weld or function weld in one of the page's own <script> blocks writes to window.weld and destroys the exports; a const weld shadows them for the rest of that script. Both are silent server-side, so a page that exports anything and also declares weld at the top level fails to compile. The check is conservative: it looks only at declarations at the start of a line, so an occurrence inside a nested block or a string is not mistaken for one, and a name introduced by an external <script src> cannot be seen at all.

Includes and layouts

A shared header, nav or footer lives in its own file and is pulled in with <weld src="...">:

<!doctype html>
<weld src="../partials/header.html"></weld>

<main>
  <weld var="page">return { name: 'about' };</weld>
</main>

<weld src="../partials/footer.html"></weld>

Paths resolve relative to the file doing the including, and includes may nest. The tag must be empty and cannot also carry var.

Includes cost nothing per request. They are expanded once at compile time, before the page is scanned, and the included markup is merged into the surrounding static runs. A page with two partials still writes the same number of buffers as one without.

Because expansion happens before scanning, an included file behaves exactly as if its contents were pasted in: its <weld> setup blocks join the page's setup, its <weld var> blocks become the page's request blocks, and a variable name used by both the partial and the page is caught as a duplicate at compile time.

A cycle is refused rather than followed, and nesting is capped at 16 levels. page.dependencies lists the files pulled in, which is what watch uses.

File-based routing

Mount a directory and every .html file in it becomes a route:

app.use(router(path.join(__dirname, 'pages')));
FileRoute
pages/index.html/
pages/about.html/about
pages/blog/index.html/blog
pages/blog/[slug].html/blog/:slug

A [name] segment becomes request.params.name, decoded. Dotfiles are skipped, symlinked directories are not followed, and non-GET methods pass straight through.

The route table is built once at startup and never consulted against the filesystem at request time, so a traversal attempt has nothing to match. /blog/%2e%2e, /%2e%2e/%2e%2e/etc/passwd, a null byte and malformed percent-encoding are all rejected outright. Static routes are a single Map lookup; parameterised ones are compared only against candidates with the same segment count.

Content-Security-Policy

The emitted <script> is inline, which a strict policy such as script-src 'self' blocks outright — the page renders and the data silently never arrives. Set a nonce on res.locals and it is applied automatically:

app.use((req, res, next) => {
  res.locals.cspNonce = crypto.randomBytes(16).toString('base64');
  res.setHeader(
    'content-security-policy',
    `default-src 'self'; script-src 'self' 'nonce-${res.locals.cspNonce}'`
  );
  next();
});

Both res.locals.cspNonce and res.locals.nonce are recognised, so the common helmet setups need no configuration. The emitted tag becomes <script nonce="...">.

A nonce that is not base64-shaped, or is shorter than 8 or longer than 256 characters, is refused rather than escaped. Escaping it would produce a tag the policy does not match, which fails as a silently blank page instead of a visible error.

Hot reload

Recompile a page when its file changes, so a running server picks up edits without a restart:

const page = load(path.join(__dirname, 'page.html'));

if (process.env.NODE_ENV !== 'production') {
  watch(page);
}

Setup blocks re-run too, so a change to setup code takes effect and not only the markup. Files pulled in by <weld src> are watched as well, so editing a shared header rebuilds the pages that include it.

Rapid writes are debounced into one rebuild, in-flight requests keep the page they already resolved, and watcher.close() stops it. Watching the same page twice returns the existing watcher rather than opening a second one.

Development only. It holds an open file handle per watched file, and a production server has no reason to re-read pages it compiled at boot.

Using Express

render() needs only response.write(chunk) returning a boolean and a 'drain' event. Express's res is an http.ServerResponse and does not replace either, so it works unchanged.

const page = load(path.join(__dirname, 'views', 'profile.html'));

app.use('/docs', express.static(path.join(__dirname, 'docs')));

// Already an Express handler: renders, ends, and forwards errors to next.
app.get('/profile', page.handler);

One version-dependent gotcha. Express 5 auto-forwards rejected promises from async handlers; Express 4 does not — an async handler that throws without an explicit try/catch … next(err) leaves the request hanging until timeout. The snippet above is safe on both.

Failures are atomic, so next(err) reaches Express's error handler with nothing yet written and it can send a real 500.

API

Stability: pre-1.0. Everything below works as described and is covered by tests, but nothing is frozen. load, router, page.handler, page.render and the export rules are settled in shape and unlikely to change. The browser-side contract — a var block assigning to window.weld — was settled deliberately before wider adoption and is now intended to be stable; it is what a page author programs against, so it is the one thing here that will not be changed casually. Treat scan, serialize, assertSerializable and page.parts as internals that happen to be exported.

load(filename)

Returns a page synchronously and compiles it in the background, so a server needs no async wrapper. Requests arriving before compilation finishes wait for it. Loading the same resolved path again returns the same page rather than compiling it twice.

const home = load(path.join(__dirname, 'views', 'home.html'));

app.get('/', home.handler);
app.listen(3000);

A compile failure is reported on stderr immediately and rejects page.ready; requests then fail through next. To stop the process instead of serving errors, add page.ready.catch(() => process.exit(1)).

A failed compile is retried. Only a successful compile is cached, so correcting the file is picked up by the next request — the running server recovers without a restart, holding the same page object. A page that stays broken is recompiled on each request, measured at 0.45 ms versus 0.012 ms for a healthy one, so a persistent failure costs throughput until it is fixed.

page.ready

The compile promise, for callers who want to await compilation or fail at boot. It is a getter, not a fixed promise: reading it after a failure starts a fresh compile rather than replaying the old error, which is what lets a corrected file recover without a restart.

const page = load('./views/home.html');

// Fail at boot rather than serving errors.
await page.ready;

// Anything that reads the compiled page must await it first.
await page.ready;
console.log(page.dependencies);   // [] before this point, populated after

You rarely need it: handler, render and renderToBuffer all await compilation internally.

await compileFile(filename)

Reads and compiles an HTML file. Runs all setup blocks once. Returns a frozen page object. The path is resolved against process.cwd(), so pass an absolute path built from __dirname.

await compileSource(input, options?)

Same, from a string or Buffer. Options, all optional:

OptionDefaultEffect
filenamepage.html What require, __filename, __dirname and <weld src> resolve against inside the page.
maxExportBytes1048576 Emitted <script> bytes one render may produce. Must be an integer of at least 1024; validated at compile time, so a bad value throws here rather than on the first request.
warnOnMutableSetuptrue Set false to silence the shared-setup-scope warning.

Passing a non-object, a non-string filename, or an out-of-range maxExportBytes throws TypeError.

page.handler(request, response, next?)

A ready-made route handler. Renders the page, ends the response, and forwards any failure to next. Sets content-type: text/html; charset=utf-8 only if nothing has set it already.

app.get('/', page.handler);

Called without next, it returns the promise instead, so a vanilla server can handle the failure itself rather than having it swallowed. You must attach a catch. Passing it straight to http.createServer(page.handler) leaves the rejection unhandled, which terminates the process on the first failing block:

http.createServer((request, response) => {
  page.handler(request, response).catch((error) => {
    console.error(error);
    if (!response.headersSent) response.writeHead(500);
    response.end('Internal Server Error');
  });
});
page.render(request, response)

Streams the page, writing static buffers directly and awaiting 'drain' on backpressure. request is passed to every handler.

await page.renderToBuffer(request?, response?)

Renders to a single Buffer. Also resolves blocks concurrently, but copies the whole page, which measured about 16x more per-request overhead than render(). Use it when you need the bytes rather than a response.

page.filename · page.parts

The resolved path and the compiled part list ({ type: 'html', buffer } and { type: 'request', varName, handler }).

The original source Buffer is not retained. Each static run is copied into its own allocation at compile time so the source can be collected — holding it would make every page cost its own size twice, which matters once an app has hundreds of pages.

router(directory)

Maps a directory of .html files to routes, resolved once at startup. Returns an Express-compatible middleware. middleware.routes lists what was mounted. It takes no options: the directory is the whole configuration. Throws if directory is not a non-empty string, or does not name a directory.

watch(page, options?)

Recompiles the page when its file, or any file it includes, changes. Development only — it holds open file handles. Returns a watcher with close(), page, and a live files list. Watching the same page twice returns the existing watcher.

const page = load('./views/home.html');
if (process.env.NODE_ENV !== 'production') watch(page);

The include graph is not known until the page has compiled, so the watched set is not fixed when watch() is called. It is reconciled against page.dependencies once the initial compile settles and again after every successful rebuild — so the sequence above works with no await between the two calls, an include added later starts being watched, and one removed stops.

options.onChange(page) is called after each rebuild is triggered. options.dependencies pins the watched set to exactly that list plus the page itself, for related files that are not expressible as includes; reconciliation is then skipped, so includes are not added to a pinned list. A file that cannot be watched is reported on stderr and does not stop the others.

close() closes every handle, cancels any rebuild still inside the debounce window, and stops later reconciliation from reopening anything. clearLoaded() closes all open watchers.

page.dependencies · page.invalidate()

The absolute paths pulled in by <weld src>, transitively, and a manual rebuild trigger. On a loaded page dependencies is [] and parts is undefined until the first compile finishes — await page.ready first. invalidate() drops the compiled page so the next use rebuilds from disk, re-running setup blocks, and returns the new compile promise.

await shared(key, factory)

Process-wide resource cache. The factory runs once per key; concurrent callers receive the same promise, and a rejected factory is not cached. Available inside setup blocks.

clearShared()

Empties the cache. Intended for tests.

clearLoaded()

Empties the page cache and closes every open watcher. Intended for tests.

serialize(value, budget?) · assertSerializable(value, budget?) · MAX_DEPTH · MAX_EXPORT_BYTES

The export serializer, its validator, the depth limit (64), and the default size limit (1048576). Both accept an optional budget and create a fresh one otherwise, so called without it each call gets the full limit. assertSerializable validates without producing output, so it checks structure and the walk's lower bound but not the exact byte count.

scan(input)

The low-level scanner. Returns { source, parts } with byte offsets.

Errors

Scan-time problems throw WeldSyntaxError (a SyntaxError) carrying offset, line and column, with the filename prefixed to the message. Compilation happens at startup, so a malformed page is caught before any traffic reaches it.

It does not stop the process. load() reports the failure on stderr immediately and rejects page.ready; requests for that page then fail through next while the rest of the server keeps serving. Only a successful compile is cached, so fixing the file recovers on the next request. To exit at boot instead, await it yourself:

await page.ready;   // or: page.ready.catch(() => process.exit(1))

Export problems throw TypeError at render time, from the request that caused them. The message names the block and the page, and the original error is kept as error.cause:

<weld var="beta"> in /app/views/profile.html: Cannot export function at $.handler

Security

<weld> is trusted server application code with normal Node.js privileges. It is not a sandbox.

An HTML file is executable code. Compiling one is equivalent to require-ing it. Never call compileFile or compileSource on a file that a user supplied, uploaded, or can edit — a <weld> block in it runs with full server privileges. Templates belong in your repository, not in a database or an uploads directory.

Request data, by contrast, cannot reach the compiler. Compilation happens once at startup from the file's bytes alone, before any request exists. A value returned from a handler is serialized as data and never evaluated server-side, and a string containing </weld> is escaped rather than reopening a block:

request.query.payload = 'require("fs"); doSomething();'
emitted: <script>(window.weld=window.weld||{}).v="require(\"fs\"); doSomething();";</script>   // inert data

One footgun to avoid. require is in scope inside var blocks too, so require(request.query.mod) loads an attacker-chosen module on every request. Never pass request data to require, fs paths, or child-process arguments.

The boundary is the export path. Only values returned from <weld var="…"> reach the client, and they are:

  • Validated and copied in a single walk, reading each property exactly once, so the value that is checked is necessarily the value written. A second pass would let an accessor or proxy return one value to the validator and another to the serializer.
  • Escaped for &, <, >, U+2028 and U+2029, so a string cannot terminate the generated <script>.
  • Rejected if they carry a __proto__ key, which would set the prototype of the client-side object rather than defining a property.
  • Depth-bounded at 64 levels, so deep nesting fails cleanly instead of exhausting the stack.

Use placeholders for SQL. db.prepare('… WHERE id = ?') binds the value as data; interpolating it into the SQL string is both slower and an injection hole.

The largest remaining hazard is not in the serializer but in scope discipline — see Request isolation.

Limitations

  • Literal <weld> and </weld> are reserved sequences anywhere in the file, including inside comments, scripts, and attribute values.
  • Nested <weld> blocks are rejected.
  • var and src are the only supported attributes.
  • Includes are flat: a page can pull in a partial, but cannot be wrapped by a layout.
  • No body parser, sessions, authentication, or database abstraction, by design.
  • renderToBuffer() copies the whole page into one buffer; render() writes the static buffers directly and is about 16x cheaper per request.
  • Exports are capped at 1 MiB per render and 64 levels of nesting. The size limit is configurable per page via maxExportBytes; the depth limit is still a constant.
  • Exported data lands on one window.weld object, so the only name a page must leave alone is weld itself.
  • watch() opens one file handle per watched file, which will hit the inotify limit on Linux at a large enough page count.
